# AGENTS.md

This file provides guidance to coding agents working with code in this repository.

## What this is

«Видео» (`io.github.haltia_de.Video`, package and command `haltia-video`; `io.github.trudenboy.Video` / `b8k-video` before 2.0, ADR 0004) — a GTK 3 (PyGObject) video program made for the Lenovo YOGA Tablet 10 (B8000-H) with the
Haltia shell ([device-lenovo-b8000h](https://github.com/haltia-de/device-lenovo-b8000h)), but a self-contained desktop program (ADR 0001 in haltia-de/haltia: device / shell / programs; programs meet the shell only through freedesktop standards — the .desktop file, logind inhibit, Unity LauncherEntry). Touch-sized cards, search, followed channels, history. Playback is `haltia-vplay` from `vplay/` here (libmpv), falling back to `mpv`. Target CPU is a slow ARMv7 tablet with an on-screen keyboard.

- No shell code: questions are `haltia_kit.dialogs` (in-window GTK dialogs; haltia-kit, package `py3-haltia-kit` 2.2.0 or later, is a normal dependency, haltia-de/kit, `/mnt/data/Projects/haltia-de/kit` locally — put it on `PYTHONPATH` to run from the repo); the look comes from the desktop's GTK theme (the shell's `b8k` theme makes header and dialogs large); the shell's touch filter buzzes, so nothing here does. `GLib.set_prgname(APP_ID)` runs before GTK is imported: it is the Wayland app id the .desktop file matches.
- The header bar shows the window buttons (the desktop's decoration-layout) except inside the Haltia shell (`ON_HALTIA`: `Haltia` in `XDG_CURRENT_DESKTOP`, which its session sets to `Haltia:GNOME`), whose own ✕ closes windows. Видео has one window: Настройки and the sign-ins are pages in it, its questions haltia-kit's dialogs.
- What still meets the shell, and degrades without it: `Player.show()` runs the shell's `haltia-focus activate haltia-vplay` (`b8k-focus` before shell 2.0) to bring the player window back (nothing elsewhere). The .desktop file's `X-Haltia-Windows=haltia-vplay;b8k-vplay` (and the same `X-B8K-*` keys for shells before 2.0, until 3.0) makes the shell count the player window as Видео's (panel, «✕»).

## Commands

There is no build step or linter config. Domain terms (Source, Channel, Followed channel, Library, Feed, Home, Scope…) are defined in `CONTEXT.md`; use them.

- Tests: `python3 -m unittest` from the repo root (stdlib `unittest`; `tests/test_renamed.py` needs haltia-kit on `PYTHONPATH`; `tests/`). Python dependencies for packaging outside a distribution are pinned in `requirements.txt` (with the non-Python ones in its comment) and `requirements-yt-dlp.txt` (yt-dlp and yt-dlp-ejs, raised on its own); keep them at what Alpine 3.24 ships and tests. The Flatpak manifest and `debian/vendor.sh` fetch the same versions by sha256: raise them there too. One test: `python3 -m unittest tests.test_library.LibraryTest.test_settings`.
- Sources are tested on recorded answers (`tests/fixtures/*.json`, replayed by `tests/replay.py`). When VK or YouTube changes what it answers: `HALTIA_LIVE=1 python3 -m unittest tests.test_live` (live checks, skipped by default) to see it, then `python3 -m tests.record [scenario ...]` to re-record (trims answers and replaces tokens) and fix what `tests/test_sources.py` then reports.

- Run locally: `./haltia-video` (needs Python 3 + PyGObject/GTK 3, `yt-dlp` with a JS runtime such as QuickJS, and `mpv` if `haltia-vplay` is absent).
- Install: `sh install.sh [ROOT] [PREFIX]` (ROOT empty or `/` = this system; PREFIX `/usr/local` unless given, the Alpine package passes `/usr`). It installs `PREFIX/bin/haltia-video`, the modules into `PREFIX/lib/haltia-video/` (the program finds them next to itself or at `../lib/haltia-video`), `vplay/haltia-vplay` as `PREFIX/bin/haltia-vplay` when it has been built, and `data/`: `io.github.haltia_de.Video.desktop` (`X-Haltia-Home=true`, `X-Haltia-Replaces=video`, `X-Flatpak-RenamedFrom` the old id; the `X-B8K-*` copies), the hicolor icon and AppStream metainfo (`<replaces>` the old id). Until 3.0 it also installs the old names: `b8k-video` and `b8k-vplay` as links, and `io.github.trudenboy.Video.desktop` with `NoDisplay=true`; and it removes the shell's old `apps.d/video.conf`. The tablet's image (device-lenovo-b8000h) pins a tag of this repository in its `linux-port/apps/sources` and runs install.sh — that repository is not edited from here: tell its session the tag and commit.
- Desktop packages, both without haltia-vplay (mpv plays; `find_player`), and without the pre-ADR-0004 names:
  - Flatpak: `packaging/flatpak/io.github.haltia_de.Video.yml` (GNOME 51; modules: `haltia-kit.yml`, a copy of haltia-de/kit's, Pillow from its sdist with pybind11 for the build, qrcode, yt-dlp + yt-dlp-ejs wheels, QuickJS, and mpv after io.mpv.Mpv's flathub recipe — LuaJIT for its ytdl hook, libass, libplacebo — on the runtime's FFmpeg; `codecs-extra` replaced ffmpeg-full from 25.08). Build here with `flatpak run org.flatpak.Builder --user --install --force-clean --state-dir=.remember/tmp/fp/state .remember/tmp/fp/build packaging/flatpak/io.github.haltia_de.Video.yml` from the repo root (the Builder Flatpak cannot see /tmp). Data lands in `~/.var/app/io.github.haltia_de.Video/`; the browser sign-in is hidden there (`/.flatpak-info`), the vault uses the Secret portal.
  - deb: `debian/` (`haltia-video`, Architecture any because of the vendored qjs; Depends python3-haltia-kit (>= 2.2.0, which brings libsecret), mpv, python3-pil, python3-qrcode). The distributions' yt-dlp (noble 2024.04, trixie 2025.04) and noble's QuickJS (2021) are too old, so `debian/vendor.sh` fetches yt-dlp and yt-dlp-ejs wheels and builds QuickJS 2025-09-13 into `/usr/lib/haltia-video/vendor/`; the program puts `vendor/` first on `sys.path` and `vendor/bin` (qjs, a `yt-dlp` launcher, which mpv's ytdl hook runs) first on `PATH`; `dh_python3` compiles the private modules. Build with `dpkg-buildpackage -us -uc -b` in `ubuntu:noble`, `ubuntu:resolute` and `debian:trixie` (`apt-get build-dep ./`), then lintian (only `no-manual-page`).
- `haltia-vplay` (C, `vplay/haltia-vplay.c`): `vplay/build.sh` cross-builds it for the tablet in the `b8000h-build:3.24` image against the keyboard build's sysroot (`OUT=` for the output; default `vplay/haltia-vplay`, gitignored); `packaging/alpine/APKBUILD`'s `build()` is the native build. Links pangocairo, wayland-client, gio-unix-2.0, mpv.
- Releases (ADR 0002 in haltia-de/haltia): SemVer `vX.Y.Z`, always three numbers — X incompatible (commands, data formats, `X-B8K-…` keys), Y features, Z fixes and packaging-only changes. The tag must equal `pkgver` in `packaging/alpine/APKBUILD` and the newest `<release version>` in `data/*.metainfo.xml`; `pkgrel=0`. Release notes are written in `NEWS.md` (newest first: `## X.Y.Z (YYYY-MM-DD)`, then `### Русский` and `### English`, each a few bullets or paragraphs on what the person will notice), both languages, before tagging; `python3 <haltia-de/ci>/news.py metainfo NEWS.md data/io.github.haltia_de.Video.metainfo.xml` then writes the metainfo's `<releases>` from it (English untranslated, Russian as `xml:lang="ru"`; validate with `appstreamcli validate --no-net`), and `apk.yml` fails a tag whose metainfo does not match (`news.py ... --check`). The shell's updater shows the Russian text as «Что нового» before installing. Pushing the tag (in its own push, after the commit) runs `.github/workflows/release.yml` → `haltia-de/ci` `apk.yml` (`arch: armv7 aarch64 x86_64`, because haltia-vplay is C: one package per architecture, armv7's under the plain name, the others as `name.<arch>.apk`; the Haltia repository files each under its architecture, for the tablet and postmarketOS): it checks the versions, builds and signs the package in an emulated Alpine 3.24 armv7 (`build-apk.sh`: installs depends/makedepends one by one, ours, py3-haltia-kit among them, from the Haltia apk repository (haltia-de/packages; a kit just released reaches it a minute or so after its own tag: tag a program that needs it after that, or rerun the failed job), then `abuild checksum` and `abuild -F -d`, which runs `check()` = `python3 -m unittest` as root), and uploads the apk and SHA256SUMS to the GitHub release. The same tag runs `deb.yml` (noble, resolute and trixie, amd64; debian/changelog must be the tag's version) and `flatpak.yml` (x86_64, the metainfo must have the tag's release) of haltia-de/ci, which add the debs, the `.flatpak` and their SHA256SUMS; every job passes `secrets: inherit`, so that the release starts haltia-de/packages' publish at once. Never delete or re-push a tag: GitHub turns its release into a draft. The tablet image installs that apk through its lock file (haltia-vplay included), so APKBUILD's `build()` is the real build. Then tell the device-lenovo-b8000h session the tag.
- Exercise a source without the UI: `python3 -c 'import sources; s = sources.load()["vk"]; print(s.search("test")[:2])'` from the repo root (`youtube` needs `yt_dlp` importable).
- Try the UI against a throwaway profile: `HOME=/some/dir ./haltia-video` (config, history, cache and accounts all live under `$HOME`).

## Architecture

- `haltia-video` — the whole app in one file: a `Gtk.Application` (`APP_ID`) with a search row (scope button, entry), four tabs (Главная = default, Подписки, Каналы, История), a gear for Настройки, and a scrolled body holding a note label plus the current content. Search results, channel search, a single channel and Настройки are "sub-pages" over the tabs: `self.sub` is a dict with `kind` (`search`, `channels`, `channel`, `settings`), the back button returns to `self.page`, and async callbacks check `self.sub is sub` / `on_sub()` to drop stale results.
- `library.py` — the Library: followed channels (with their details, `latest`, `updated`), the history (entries may carry `pos`/`duration`: how far it was watched; `resume_at()` skips the first 10 s and a watched end — under 30 s left or past 95% — and `progress()` gives the cards' strip), and the settings (`disabled`, `scope`, `sort`), the only code that reads or writes `video.json` and `history.json` (same keys as before it existed). GTK-free and GTK-thread-only by contract; callers learn of changes through `watch(fn)` with `"follow"`, `"unfollow"`, `"details"`, `"history"`, `"position"`, `"settings"` — the window reacts in `library_changed` (a follow marks the feed stale; an unfollow or new details redraw the tab). The feed display filters on `is_followed`, so an unfollow needs no edit of the cached feed. Tested in `tests/test_library.py` against a temporary directory.
- `search.py` — `view(kind, query, sources, found, loading, failed, sort)`: what a search shows (sections, the note line «Ищу…» / «Не удалось…» / «Ничего не найдено.», whether the sort switch is offered), GTK-free; `show_results` only turns it into widgets. Tested in `tests/test_search.py`.
- `signin.py` — `SignIn`, one per source that has an Account: drives the source's own steps (`login_start`/`login_poll` for `login = "code"`, `login_check` for `"cookies"`, `logout`) and exposes one `state` (`out`, `getting`, `waiting` with url/code, `checking`, `in` with name, `failed` with note). Polls every 3 s, shows a new code when one expires (up to 5), and `cancel()` stops it — the window calls that when Настройки is left. Gets `run` (the window's `work`) and `later(ms, fn)` (a GLib timeout) injected; tested with a fake source and timer in `tests/test_signin.py`. Настройки only draws the state; becoming signed in or out forgets that source's Главная and all searches (`_signin_changed`). Bringing an Account's channels over stays in the window (`import_subscriptions` → `Library.follow_all`).
- `player.py` — `Player`: starts haltia-vplay (mpv on a desktop) with `input-ipc-server=$XDG_RUNTIME_DIR/haltia-video/mpv-<pid>-<n>.sock` (haltia-vplay passes `name=value` options on to libmpv; checked with libmpv 0.41 in Alpine) and reads mpv's JSON IPC on a thread of its own. `state` is None or `{"video", "pos", "duration", "paused"}` (pos told to the second); `play`/`toggle`/`seek`/`stop`, `show()` runs `haltia-focus activate haltia-vplay` (whichever of haltia-focus, b8k-focus is on PATH). One video at a time; the socket closing (window closed, video ended) ends the state. No player is left running unseen: each run keeps its process, and one that cannot be told `quit` (still starting, given up on after 15 s, connected only after it was stopped) is terminated; one that exits ends the loading at once; the window's `do_shutdown` stops it (and so writes the position down). Also builds the command line (`command()`, incl. the `ytdl-raw-options` that must repeat `js-runtimes=quickjs`; mpv always gets it, since yt-dlp's default runtime is deno alone). The player is chosen by `find_player()`: haltia-vplay (or `b8k-vplay`) when installed on PATH — the tablet's apk — else `mpv` (a desktop's deb or Flatpak bring mpv and no vplay), else None and `open` raises OSError. `spawn`/`connect`/`post` are injected; `tests/test_player.py` talks to it through a socketpair. `open(..., start=)` plays from a position (`start=` / `--start=`). For haltia-vplay (`stream_format` = `VPLAY_FORMAT`, its own ytdl-format) `open(..., resolve=)` first asks the source's `stream(video, fmt)` on a thread of its own (the bar says «загрузка…» meanwhile) and starts haltia-vplay on the answer, an `edl://` of the video and audio URLs with `ytdl=no` and the `user-agent`: a new yt-dlp process per video cost the tablet ~6 s of Python start and imports and ~17-21 s in all, the warm one in Видео ~3-4 s. When `stream` fails, haltia-vplay's own yt-dlp hook tries the page URL as before; mpv on a desktop always resolves itself. The window writes the position down (`note_position`: on a pause — leaving haltia-vplay pauses it — on close, and every 30 s), plays from `Library.resume_at`, and shows it in a bar under the cards (`make_bar`/`show_bar`): haltia-vplay pauses when left, so the bar's main button is «▶ Смотреть» (play + show), ⏸ only where the player plays on (mpv on a desktop).
- `sources/` — pluggable video sources. Any module defining a module-level `SOURCE` object is picked up by `sources.load()`; a source that fails to import is logged and skipped. The full interface (required search/channel methods, optional `warm_up`, `owns`, `home`, `ytdl_options`, and the account methods for `login = "code"` or `"cookies"`) and the video/channel dict shapes are documented in `sources/__init__.py`, which also holds `CONFIG_DIR`/`CACHE_DIR` and the shared `load_json`/`save_json` (atomic, optional 0600).
  - The http seam: each source takes `http` (anything with `get_json(url, data, headers)` / `request(url, ..., limit=)`; default `sources.net`) and its `config_dir`/`cache_dir` in its constructor; the module-level `SOURCE` uses the defaults. Tests pass `tests.replay.Replay`, a temporary directory and, for VK, a frozen `clock` (a recorded anonymous token carries a real expiry date; on the real clock the tests broke once it passed). yt-dlp calls in `youtube.py` have no seam and no tests.
  - The vault is haltia-kit's (`haltia_kit.vault`, kit 2.2.0 or later; Видео's own `sources/vault.py` moved there): `sources.vault_in(config_dir)` makes it under the schema `io.github.haltia_de.Video` (items found by `name` alone, so 2.1's are found; the first store adds `app=`), label «Видео». It keeps an Account's secrets (`video-vk.json`, `youtube-cookies.txt`) in the Secret Service through libsecret (the Secret portal in Flatpak), else as the 0600 file of that name in the config folder (the tablet has no keyring). A file found while the keyring answers moves in once; `take()` moves a cookies file the person has just put in place; `as_file()` gives yt-dlp and mpv a copy in a `haltia-vault-` folder of the runtime dir, written back at exit if yt-dlp renewed it. When the person refuses to unlock the keyring the vault raises `Locked`: a source then sets `locked`, answers as signed out and plays as a guest without dropping anything (YouTube does not ask again at every yt-dlp call), and `unlock()` asks again; `SignIn` shows the state `locked` («Связка ключей закрыта…», button «Открыть связку ключей»), also when a new sign-in could not be stored. Tests pass `vault_in(dir, keyring=None)` or `haltia_kit.testing.FakeKeyring` (`tests/test_accounts.py`) so they never touch the real keyring.
  - `net.py` is not a source: HTTP with one kept-alive connection per host and thread (TLS handshakes are expensive on the tablet's CPU) plus gzip. Use it rather than `urllib` for anything fetched repeatedly.
  - `youtube.py`: search via yt-dlp (lazy-imported because import is slow on the tablet), channel videos via the public Atom feed (exact dates, Shorts by their `/shorts/` link) plus, for the durations it lacks, one POST of YouTube's own `youtubei/v1/browse` for the channel's «Видео» tab (`_durations`; the lengths are read from the thumbnail badges' text by regex, not by walking the ~0.5 MB answer; Shorts are not on that tab and stay without; failing, the cards go without durations). `net.request` sends a dict as JSON when the headers say `application/json`; the recordings keep only the badges (`record.trim_browse`). YouTube has no guest trends and no program sign-in any more: login is a browser's cookies — `login_check(browser)` with yt-dlp's `cookiesfrombrowser` from Firefox or Chromium, offered by `browsers()` where a profile exists and not in Flatpak (`/.flatpak-info`); the account file then names the browser and nothing secret is stored — or a cookies.txt file put at `~/.config/haltia-video/youtube-cookies.txt` (the way on the tablet and in Flatpak), checked via `feed/channels` and then taken into the vault; either is passed to every yt-dlp call, `home()` returns `:ytrec` recommendations, `stream()` asks without the `web` client (its formats are all SABR now, left out, but parsing their URLs cost seconds), and `ytdl_options()` hands them to the player (`cookies-from-browser=` or `cookies=` in mpv's `ytdl-raw-options`).
  - Subtitles: Видео shows none, so `youtube._skip_captions` and `vkvideo._skip_subtitles` patch yt-dlp's extractors (once, in this process; a no-op when their insides change) to drop them from the answers before yt-dlp looks: YouTube's automatic captions came in ~157 translations, a URL each (seconds per video on the tablet), and yt-dlp 2026.08.19 fails on a VK subtitle without a title (yt-dlp PR 16761). `youtube.SUBTITLES = True` turns YouTube's back on, for when Видео shows them.
  - `vkvideo.py`: VK API (`api.vk.com`) with the anonymous token vkvideo.ru's own web client gets (`login.vk.com/?act=get_anonym_token`, public client id/secret from its scripts; cached in `~/.cache/haltia-video/vk-anonym.json`); many methods (`video.search`, `groups.search`) are refused with that token, so search goes through `catalog.getVideoSearchWeb2` (`content_type=author` for channels) and Главная through `catalog.getVideo` → `catalog.getSection` (trends). Sign-in is the TV-style code flow `auth.getAuthCode` → poll `auth.checkAuthCode` (status 0/1 waiting, others end it; a code lives ~3 min and the app requests a new one); the person's token is kept in the vault as `video-vk.json` and replaces the anonymous one. The success branch of the poll (status 2 with `access_token`, `user_id`) has not been seen live yet: `test_confirmed` pins that assumption — replace it with a recording once a sign-in is confirmed. Videos with `restriction.can_play == 0` (account- or age-restricted; no picture either) are left out. Channel ids are VK owner ids as strings (`"-55155418"` = community). Playback is plain `vkvideo.ru/video<owner>_<id>` through yt-dlp.
  - Searches go to every enabled source in parallel (`config["scope"]` = `"all"` or one source id), shown as each answers. `config["sort"]` = `"date"` (default) merges all sources' results newest first; `"relevance"` shows them per source, YouTube's section first. Sorting is done on the found (relevance) results: asking the services for date order is useless (YouTube ignores `sp=CAI=`, VK `sort=0` returns the newest of anything, matching or not). YouTube dates in result lists come from yt-dlp's `youtubetab:approximate_date` (day precision, from "3 days ago"); in channel search, text a source `owns()` (a link) goes to that source only. `config["disabled"]` lists sources switched off in Настройки; their videos are filtered out of the feed and Главная at display time. Shorts (YouTube's `/shorts/` links in search, `:ytrec` and the Atom feed; VK's `type == "short_video"`, whose search block is `data_type` `videos`) carry `"short": True`; `config["shorts"]` (absent = off, so 1.4's keys stay; `Library.shorts`, the switch «Shorts и клипы» in Настройки) shows them, and the window's `wanted()` drops them at display time everywhere but История — no picture of a hidden one is fetched, and the switch needs no new asking. The feed keeps `FEED_MAX` of each kind, so hidden Shorts push no videos out.
- Followed channels carry optional details (avatar, handle, subscribers, description) plus `latest` (newest video time, from each feed load) and `updated` (when details were fetched). Channels followed from a card have only an id and title; `Library.lacking_details()` names them (and week-old ones), and `refresh_channels` asks the sources in the background when Каналы opens.
- Caching (the tablet is slow, so most of the app is built around not waiting):
  - `kept.py` — `Kept`, one kept collection: `get(key)` returns what is kept (or None) and fetches again when older than its ttl; one fetch per key; a failure keeps the old value and is not retried for 2 minutes; `invalidate(key)` (also marks a fetch under way as old on arrival) and `forget(key)`; `watch(fn)` → `fn(key, error)`. It runs fetches through the window's `work` and calls `prepare(key)` on the GTK thread for what the fetch needs, so it is GTK-free and tested with a synchronous runner and a fake clock (`tests/test_kept.py`).
  - The window has four: `feed` (key `"feed"`, 30 min, on disk in `~/.cache/haltia-video/feed.json`, value `{"videos", "latest"}`; `latest` goes to `Library.note_latest`), `home` (key = source id, 60 min, on disk in `home.json`), `searches` (key `(kind, source id, query)`, 10 min) and `channel_videos` (key `(source, id)`, 15 min). Pages read them on every draw; watchers redraw the page on show. A follow or a source switched back on invalidates the feed / that Главная; signing in or out forgets that Главная and all searches.
  - The feed fetches all channels in parallel; channel detail refreshes too.
  - `Thumbs`: 4 workers fetch and decode JPEGs off the GTK thread — decoding is `pictures.decode` (Pillow → `Pixbuf.new_from_bytes`), never gdk-pixbuf's loaders: on Alpine they are all glycin in bwrap, and one deadlocked loader froze every GdkPixbuf call in the program, the GTK thread included (without Pillow, gdk-pixbuf one picture at a time) — a disk cache by URL SHA-1 (pruned at start to 30 days / 150 MB), an in-memory LRU of decoded pixbufs bounded by bytes (`pictures.Recent`, `PIXBUFS_BYTES` = 16 MB, some eighty cards: the tablet has 1 GB), one in-flight fetch per URL, and fetches for cards already destroyed are dropped (tracked by each image's `destroy` signal, since cards are built before `set_content` swaps the page).
  - `grid()` builds the first 9 cards at once and the rest in low-priority idle batches.
- Threading: source calls block on network, so they run through `Video.work(func, *args, done=...)` on a 6-worker pool, with `done(result, error)` delivered on the GTK main loop via `GLib.idle_add`. Never touch GTK widgets from worker threads.
- State files (under the XDG base directories, `sources.xdg()`, so Flatpak's own ones apply): followed channels and settings `~/.config/haltia-video/video.json`, history `~/.local/share/haltia-video/history.json` (capped at 100), both owned by `library.py`; accounts: `video-youtube.json` (not secret) and, through the vault, `video-vk.json` and `youtube-cookies.txt`. 1.x kept them in `~/.config/b8k/` and `b8k-video` folders: `renamed.move_old()` runs first thing in `__main__` (before the Library and the sources open anything) and moves them over once, leaving links at the old places (haltia-kit's `paths.migrate_dirs` for the folders; until 3.0; `tests/test_renamed.py`).
- The player: `haltia-vplay --title T URL [option=value ...]` (`vplay/haltia-vplay.c`, moved here from the shell repo; `b8k-vplay` is a link to it until 3.0); extra mpv options after the URL override its defaults, so `ytdl-raw-options` passed for cookies must repeat its `js-runtimes=quickjs`. Its main thread renders frames and handles Wayland, so it makes no call there that waits on mpv's core (`mpv/render.h`): the video's size comes as observed properties, commands and `pause` go async, and the logind Inhibit runs on a thread of its own (`hold_run`). It draws no close button (the desktop's closes it), pauses when another window takes the screen, and keeps the screen on through logind while it plays. `Player` finds it on PATH (`shutil.which`).
- The player window's app id is `haltia-vplay` (other programs, Файлы, open it too, by its old name for now); the .desktop file names it and the old `b8k-vplay` in `X-Haltia-Windows` / `X-B8K-Windows`.

## Conventions

- User-facing strings are Russian; code, comments, and commit messages are English (commit subjects are full sentences ending with a period).
- Comments explain *why*, usually a tablet constraint (slow CPU, on-screen keyboard covering the window, touch targets). Keep that density and tone.
- Style follows the existing code: `%`-formatting, no type hints, `# SPDX-License-Identifier: GPL-2.0` header on every file.
- UI layout decisions are driven by the on-screen keyboard: the window must fit the space the keyboard leaves (see the comment on the scrolled body), and no entry should take focus unasked.
